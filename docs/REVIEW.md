# 代码审查与改进记录

本轮以 `9c6a156` 为基线，目标为 1,000 个长连接，覆盖 Go 封装层的生命周期、持久化、准入、配置与持续验证。客户端授权在新连接时实时查询，只合并正在进行的同节点查询。配置按统一新结构交付，移除了重复旧字段。

## 已修复的问题

| 问题 | 改进 | 验证 |
|---|---|---|
| 状态持锁执行同步写盘，签证期间缺少心跳 | 单任务合并运行状态，I/O 移出状态锁；systemd 状态写入 `/run/derper-go`；启动阶段持续心跳 | 假时钟心跳、写入失败恢复、慢写不阻塞更新、PID 复用及停止状态 |
| TXT 清理错误中断已通过验证的签证 | 证书签发与清理分别报告；清理归属日志、退避窗口独立保存 | 有效证书在删除失败后仍可用、跨重启重试、外部修改拒绝删除 |
| 连接及准入缺少资源上限 | 默认 2,048 个 TCP 连接、32 个并行查询、128 个总准入请求；排队与查询共享 3 秒预算 | 原生 DERP 升级后仍计数、重复关闭、共享查询取消、队列与超时 |
| 关闭调试日志后仍进行消息格式化 | 格式化前检查 `slog.Enabled` | 全量回归与独立 profiling |
| Cloudflare 异常响应被归入普通 API 错误 | 区分 HTTP、API、协议错误；保留状态及重试原因，隐藏正文 | 畸形 JSON、缺少字段、响应上限、凭据及错误正文保护 |
| 重试运算可能溢出，多个维护循环各自计算退避 | 共享有界退避、正向抖动及 Retry-After 解析；保留跨重启等待窗口 | 超长值、日期、模糊测试与签证/清理重启恢复 |
| 初始化预检不完整，已准备安装难以继续 | 核对实际绑定 IP 的 HTTPS/STUN/HTTP；提前验证单元、证书及 Mesh 密钥；继续已批准安装 | 监听冲突、安装/启动失败、锁交接及身份保留 |
| 配置字段与运行职责分散 | `relay`、`http`、`admission`、`mesh`、`bootstrap_dns` 分组；时间使用 Go duration 字符串；增加 `config show --effective` | 严格字段校验、有效配置重新读取、初始化和发行包检查 |
| 外部准入缺少完整请求及故障策略边界 | 保留来源 IP；明确拒绝、主动取消、资源耗尽与服务故障分别处理；默认故障拒绝 | 明确拒绝不受 fail-open 覆盖、网络超时、取消、重定向及并发回收 |
| Mesh 自连接占用额度，入站模式显示不准确 | 识别服务端身份并关闭自连接；单独显示入站互联状态 | 双向跨节点转发、额度为 1 时忽略本机项、密钥快照及关闭等待 |
| bootstrap 请求可能演变为任意解析入口 | 仅提供允许域名的缓存；隐藏域名按来源及 TXT 百分比返回；后台有界刷新 | 隐藏记录不泄露、请求不发起解析、解析故障保留有效缓存 |
| 测试可能把采样或取消传播误当成服务故障 | 采样独立计时；保留采样失败；以客户端查询生命周期核对并发额度；故障场景未完成时禁止通过 | 时长校验、延迟查询恢复、采样计数、交付门禁测试 |

身份、账户、证书、DNS 归属及安装日志继续使用原子发布和持久化同步；运行快照采用不同写入入口。数据帧、队列、STUN、TLS MetaCert 与 Mesh 路由机制复用 Tailscale 上游实现。

## 配置与操作

完整字段及上游参数映射见 [CONFIGURATION.md](CONFIGURATION.md)，升级步骤见 [DEPLOYMENT.md](DEPLOYMENT.md)。默认配置只需域名与邮箱；高级字段可省略。实验性 ACE、GCP/EAB、IP 证书、setec 和 `rate-config` 不在已选生产范围。

配置展示不输出密钥内容。控制器地址展示移除查询参数，初始化摘要明确显示控制器故障策略。Cloudflare 与 Mesh 密钥通过独立 systemd 凭据传入；旧的清空凭据列表覆盖文件应在升级窗口移除。

## 性能证据的解释

完整方法见 [VALIDATION.md](VALIDATION.md)。受控工作流将服务端限制为 2 CPU、2 GiB，客户端使用另外的 CPU；使用 1,000 个合成 DERP 客户端、本地模拟 tailscaled 与 1,200 字节不透明载荷。三组同机成对测试分别持续转发 10 分钟，偶数轮交换版本执行顺序。

[最终工作流 41168731792](https://github.com/gatework/derper-go/actions/runs/41168731792) 全部通过。基线为 `9c6a156`，受测运行时代码为 `576ac17`；之后的 `729f521` 仅细化初始化摘要和入站 Mesh 状态，不改变数据转发路径。原始附件由工作流保留，精简数据见 [2026-10-31.json](benchmarks/2026-10-31.json)。

| 轮次 | 基线 Mbps | 改进后 Mbps | 基线 P99 µs | 改进后 P99 µs | 基线 CPU % | 改进后 CPU % |
|---|---:|---:|---:|---:|---:|---:|
| 1 | 703.50 | 702.69 | 10651 | 10506 | 177.64 | 180.58 |
| 2 | 746.43 | 724.82 | 10194 | 11021 | 185.03 | 188.38 |
| 3 | 695.55 | 699.91 | 11176 | 11115 | 176.76 | 185.53 |

成对比值的中位数：吞吐变化 -0.11%，P99 变化 -0.55%，CPU 利用率变化 +1.81%。吞吐与尾延迟符合预设门槛；本轮未观察到明显吞吐增益。测量区间累计分配（包含客户端收尾）约减少 23.02%，各轮改进后峰值 RSS 约 50–51 MiB。CPU 百分比以单个 CPU 为 100%，服务端上限为 200%。

慢接收端、突发重连、tailscaled 延迟及恢复场景的客户端连接/载荷校验错误计数均为 0，采样失败为 0。改进后各场景冷却时 FD 为 15、goroutine 为 15、连接配额为 0，与该轮初始状态一致。慢接收端允许上游队列丢弃拥塞数据，错误计数不代表无丢包。

延迟查询场景中客户端查询峰值为 32；模拟服务处理器峰值为 33，其中可能包含取消传播期间尚未退出的处理器。两项指标保留在原始数据中。

该轮单独 profiling 的 CPU 样本约 65% 位于系统调用，AES-GCM 加解密约 4.7%。互斥等待样本约 24 ms，状态锁未出现在主要热点中。分配样本主要覆盖缓冲及 TLS 建连；累计 profile 包含启动，不能当作每包分配量。数据支持继续复用上游数据面，没有依据为包装层加入额外缓冲池或重写发送路径。

96 MiB 与 256 MiB 的短时预算试验均无持续 GC；不能根据单次吞吐差异认定更大的预算普遍更快。生成单元移除了固定 96 MiB 限制，保留管理员通过 systemd 环境设置预算的方式。

[运行时代码 CI](https://github.com/gatework/derper-go/actions/runs/41169933916) 同时通过全量 race、vet、Staticcheck、解析器模糊测试、漏洞可达性扫描、双架构原生发行包与真实 systemd 验证。

以上结果限定于明确的 CI 负载与环境。连接总量上限用于保护资源；大于 1,000 个节点、不同帧大小、真实控制面和公网链路应按相应负载另行测量。生产升级仍按部署窗口安排。
